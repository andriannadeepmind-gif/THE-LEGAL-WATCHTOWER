## Α. Γιατί ΟΧΙ «σύγκριση με το αποτύπωμα» — η ανώτερη σύλληψη

Η προφανής υλοποίηση (σύγκρινε το .hash του άρθρου, skip αν ίδιο) κουβαλά την
κλασική παγίδα του incremental build: το .hash σφραγίζει το ΚΕΙΜΕΝΟ, όχι τον
GENERATOR. Αλλαγή στο HTML template με ίδιο κείμενο ⇒ ίδιο hash ⇒ skip ⇒
STALE δημοσιευμένη έξοδος — και η «λύση» θα ήταν χειροκίνητο version bump =
φρουρός που ξεχνιέται, όχι δομή. Απορρίφθηκε.

Η ανώτατη μορφή: **η παραγωγή είναι φθηνή (CPU/strings) — ακριβό είναι το IO**
(12.370 αρχεία astikos μέσα από Windows bind-mount). Άρα: παράγονται ΟΛΑ,
πάντα, όπως στο full run· και η ΜΙΑ έδρα εγγραφής συγκρίνει τα ΠΡΑΓΜΑΤΙΚΑ
bytes με τον δίσκο και γράφει ΜΟΝΟ σε διαφορά. Ισοδυναμία με πλήρη επανεγγραφή
ΕΚ ΚΑΤΑΣΚΕΥΗΣ — δεν υπάρχει κλειδί/cache/έκδοση που να μπορεί να ξεσυγχρονιστεί.

## Β. Η έδρα

`write-utf8-file` (filesystem.lisp — από εκεί περνούν ΟΛΑ τα per-article
artifacts ×5 μορφές + dataset αρχεία): `%file-bytes-equal-p` (stat μήκους →
πλήρης σύγκριση· IO σφάλμα ανάγνωσης ⇒ επανεγγραφή, ποτέ ψευδές «αμετάβλητο»)
→ `(values path :written|:unchanged)`. Αμετάβλητα αρχεία: ΑΝΕΓΓΙΧΤΑ (mtime
διατηρείται ⇒ καθαρό git status, μηδέν IO). `write-article-formats` επιστρέφει
μετρητές· `write-corpus-files` αναφέρει ΤΙΜΙΑ «Χ γράφτηκαν, Υ αμετάβλητα» —
κανένα σιωπηλό skip.
